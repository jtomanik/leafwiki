# Backend i18n Catalog

LeafWiki renders in-scope backend-originated CLI, API, and MCP messages through an English-only `nicksnyder/go-i18n` catalog. The rollout is tracked by `docs/plans/go-i18n-rollout.PLAN.md` and the originating thread `codex://threads/019ea755-a3e3-7571-a8cf-c70a33fea656`.

## Contract

- Code owns emitted message IDs. Registry entries live in `internal/localization/messages.go` as extractable `i18n.Message` literals.
- The committed English catalog is `internal/localization/locales/active.en.toml`.
- Runtime is English-only. LeafWiki does not negotiate locale from headers, config, CLI flags, environment variables, MCP metadata, or user preferences in this phase.
- Compatibility fields stay in place. API and MCP errors keep `code`, `messageId`, rendered `message`, `template`, and `args` where those fields already exist.
- Positional compatibility args are exposed to `go-i18n` templates as `Arg0`, `Arg1`, and so on. Existing `%s` templates remain compatibility data.
- Rendered localized messages must be stable catalog prose. Do not make catalog messages pass-through wrappers around `err.Error()` or arbitrary runtime text; preserve raw failure details in compatibility args, protocol metadata, logs, or adjacent dynamic detail fields instead.
- Shell wrapper help text, error prefix text, validation error bodies, and dry-run/status lines come from generated English shell variables in `scripts/run_messages.sh`, validated by `internal/localization/shell`. Option-specific validation details may still append runtime flag names, paths, or secret-redacted values; do not treat those dynamic values as catalog IDs.

## Workflow

After changing registry messages:

```sh
tmpdir="$(mktemp -d)"
go run github.com/nicksnyder/go-i18n/v2/goi18n extract -outdir "$tmpdir" ./internal/localization
cp "$tmpdir/active.en.toml" internal/localization/locales/active.en.toml
rm -rf "$tmpdir"
# If the generated shell variables drift, regenerate scripts/run_messages.sh with
# internal/localization/shell.GenerateRunMessages and commit the result.
go test ./internal/localization/shell -run TestRunMessagesExportMatchesGeneratedFile -count=1
make lint
bash scripts/check-i18n-catalog.sh
```

`scripts/check-i18n-catalog.sh` verifies focused localization tests, extractor reproducibility, generated shell message data, absence of `translate.*` files, catalog-derived E2E prose-oracle checks, and API success/status payload checks. This remains a sibling policy gate after the first golangci-lint migration slice because moving catalog drift and non-Go i18n scans into analyzers would require changes under `internal/analysis/`, which are outside the current implementation scope. The checked-in script uses standard `go`/`python3`/`rg` tooling; agents may still invoke it with the local `rtk` wrapper.

## Test Policy

Behavior tests for localized CLI, API, and MCP messages should assert stable semantics first: `code`, `messageId`, semantic data attributes, typed IDs, or protocol fields. English prose assertions are allowed only when rendered English is the behavior under test, for backward compatibility checks, for user-authored content, for accessibility text when text is the behavior, and for documented internal/log/redaction cases.

Frontend API error handling displays the backend-rendered `message` and preserves `code/messageId` for semantic attributes. The frontend error catalog may remain for legacy UI copy, but it is not the source of backend-originated API messages.
